# ANTHROPIC TOOL USE RULES 🛠️

## Overview

Rules for optimizing AI assistant code generation using Anthropic's Advanced Tool Use patterns. These rules focus on reducing token consumption (30-85% savings) while maintaining code quality and generation speed.

Based on: https://www.anthropic.com/engineering/advanced-tool-use

---

## Rule 1: Tool Search & Dynamic Selection

### Description
Load and select only necessary tools/APIs at runtime, not all available tools upfront.

### Key Patterns

#### Tool Search Skill
```
Before generating code:
1. Describe the task and its boundaries
2. Find relevant tools/APIs from the available list
3. Generate code using only selected tools
4. Skip unnecessary context/tools
```

**Example Implementation:**
```
/prompts:tool-search "Write a script for GitHub + Jira integration"
→ Codex selects only GitHub and Jira APIs
→ Skips Slack, Google Drive, other APIs
→ Saves ~85% of prompt context tokens
```

#### Benefits
- **Massive Token Savings**: 85% reduction in initial context
- **Faster Generation**: Smaller context window = faster inference
- **Reduced Hallucination**: Model focuses on relevant tools only

### Implementation Steps

1. Create a skill in `~/.codex/skills/tool-search/SKILL.md`
2. Define: "First describe the task, find needed instruments/APIs from [LIST], generate code only with them"
3. Use prompt prefix `/prompts:tool-search` when requesting code

## Rule 2: Programmatic Tool Calling

### Description
Generate one orchestrator script instead of sequential tool calls. Let the script manage intermediate results locally without re-processing by the model.

### Key Concepts

#### Single Orchestrator Pattern
Instead of:
```
Tool Call 1 → Model processes → Tool Call 2 → Model processes → ...
```

Generate:
```
Python/JS Orchestrator Script that:
- Calls all tools directly
- Processes results locally
- Returns only final summary to model
```

#### Code Example
```python
# Generated by Codex
import asyncio

team = await get_team("engineering")  # Your API
expenses = await asyncio.gather(
    get_expenses(emp_id) for emp_id in team
)

# Process locally, only return summary
budget_exceeded = [e for e in expenses if e.amount > limit]
print(summary(budget_exceeded))  # Final output only
```

#### Token Savings Breakdown
- **Step Reduction**: Multiple model inference passes → single pass
- **Context Reuse**: Intermediate data stays local, doesn't bloat prompts
- **Savings**: ~37% reduction + significant speed improvement

### Implementation Guidelines

1. Request: "Generate a Python script that orchestrates [tools]"
2. Don't ask for step-by-step API calls
3. Let the script handle intermediate results
4. Only pass final results back to model

## Rule 3: Tool Use Examples (In Context)

### Description
Include 1-5 realistic examples for each tool/API in your skills and prompts. Dramatically improves accuracy.

### Example Format

In `SKILL.md`:
```markdown
### GitHub API Examples
- List issues: `list_issues(repo="owner/repo", state="open")`
- Create ticket: `create_ticket(title="bug", priority="high", labels=["prod"])`
- Update PR: `update_pr(pr_id=123, status="review_requested")`

### Jira API Examples
- Create issue: `create_jira(project="PROJ", issue_type="bug", assignee="user@example.com")`
- Transition: `jira_transition(ticket_id="PROJ-123", status="In Progress")`
```

#### Benefits
- **Accuracy Boost**: ~90% improvement in correct API usage
- **Fewer Errors**: Reduces hallucinated parameters/endpoints
- **Less Rework**: Fewer regenerations needed

### Best Practices

1. Place examples after tool descriptions
2. Use realistic, copy-paste-ready calls
3. Show both simple and complex examples
4. Include common error cases and how to avoid them

## Rule 4: Mandatory Workflow: Plan → Read → Patch → Verify → Document

### Description
Enforce a strict 5-step cycle for every code generation request. Prevents "rewrite everything" behavior.

### Step-by-Step Process

#### 1. **Plan**
- Summarize the task in 3-5 bullet points
- Clarify boundaries and scope
- Identify affected files/modules

#### 2. **Read**
- Read only relevant files (target area + context)
- Limit: N lines around changes, not entire codebase
- Skip unnecessary modules

#### 3. **Patch**
- Generate minimal diffs (changes only)
- Don't rewrite working code
- Focus on the specific task

#### 4. **Verify**
- Provide test command or verification steps
- Example: `npm test`, `pytest tests/`, `./validate.sh`
- Ensure generated changes pass checks

#### 5. **Document**
- Update related comments/docstrings
- Update API docs if interfaces changed
- Keep docs in sync with code

### Example Workflow

```
Task: "Add Slack notification to GitHub Actions workflow"

[PLAN]
- Add Slack bot token to GitHub Secrets
- Modify .github/workflows/ci.yml
- Add notification step after tests pass
- No impact on other workflows

[READ]
.github/workflows/ci.yml (lines 1-50)

[PATCH]
- Add uses: slackapi/slack-github-action@v1
- Configure with webhook URL from secrets
- Keep existing steps unchanged

[VERIFY]
npm run test:ci
cat .github/workflows/ci.yml | grep slack

[DOCUMENT]
- Update README.md: "Slack notifications configured for CI"
- Add comment in workflow: "// Slack notification on success"
```

## Rule 5: Token Optimization Techniques

### Description
Minimize token usage through selective reading, context reuse, and smart prompting.

### Core Principles

#### 1. **Don't Re-read Everything**
- Read incrementally: narrow scope first
- Use file-specific reads, not full project dumps
- Skip unrelated modules

#### 2. **Leverage Existing Documentation**
- Reference `docs/` and `tasks/rfc/` instead of re-asking
- Point to architecture docs for context
- Use READMEs instead of describing from scratch

#### 3. **Multi-Pass Narrow Reads vs. Single Massive Read**
❌ **Bad**: "Read entire `/src` folder" (10,000 lines)
✅ **Good**: "Read only `/src/api/github.js` lines 50-100" (50 lines)

**Anthropic Principle**: Many small focused queries use fewer tokens than one giant query.

#### 4. **Request Chunking**
Break large tasks into smaller, focused requests:
```
Request 1: "Plan the refactoring"
Request 2: "Read current API schema"
Request 3: "Implement changes"
Request 4: "Update tests"
```
Each request is smaller and more focused.

### Implementation Checklist

- [ ] Always specify scope: files, line ranges, modules
- [ ] Say "no" to "read entire project"
- [ ] Ask: "What minimal context do I need?"
- [ ] Use existing docs links instead of inline explanations
- [ ] Split complex tasks into 3-5 focused requests

## Rule 6: Tool-Aware Context Management

### Description
Properly handle tool output to prevent context bloat.

### Output Handling Rules

#### Large Output Problem
```
Command: git log --all
Output: 50,000 lines of logs
Problem: All 50,000 lines go into prompt (massive token waste)
```

#### Solution: Summarize, Don't Include
```
Command: git log --all
Output: First summarize (120 chars):
  "Last 5 commits: fix-bug, refactor-api, update-docs, add-tests, bump-version"
Include: Only this summary, not full logs
```

#### Rules for Tool Output

| Tool Output Size | Action |
|---|---|
| < 200 chars | Include fully |
| 200-2000 chars | Include, but ask to summarize |
| > 2000 chars | Always summarize (1-3 sentences) |
| Logs/Stack Traces | Extract key error, skip noise |
| Test Output | Show failures only, skip passes |

### Implementation Guide

When invoking tools, always apply:
```
if output.length > 2000:
    return summarize(output, max_chars=200)
else:
    return output
```

### Examples

**Before (Bad):**
```
Error in /src/components/Button.js at line 45:
TypeError: Cannot read property 'onClick' of undefined
    at Button.handleClick (/src/components/Button.js:45:12)
    at React.eventPlugin.executeDispatch (/node_modules/react/dist/react.js:12391:28)
    ... [30 more lines] ...
```

**After (Good):**
```
Error: "Cannot read property 'onClick' of undefined" in Button.js:45
Missing prop validation in Button component
```

## Rule 7: Configuration for Codex CLI

### Description
Configure Codex CLI settings to maximize token efficiency while maintaining quality.

### Configuration File
Path: `~/.codex/config.toml`

#### Recommended Settings
```toml
[model]
# Balance quality and token usage
reasoning_effort = "high"  # Use efficient reasoning, not maximum
model = "gpt-4-optimized"
max_tokens = 4000

[tools]
# Programmatic tool calling
prefer_orchestrator_scripts = true
allow_tool_chaining = false  # Use script instead

[context]
# Selective context loading
dynamic_tool_loading = true  # Load tools on demand
max_context_size = 8000  # Strict limit
skill_based_context = true  # Load skills as needed

[tokens]
# Optimize token usage
summarize_large_outputs = true
max_output_chars = 2000
skip_redundant_context = true
```

### Custom Skills for Token Optimization

Create `~/.codex/skills/tool-optimizer/SKILL.md`:

```markdown
# Tool Optimizer Skill

When generating code:
1. Follow Anthropic pattern: search → script → examples
2. Load only needed tools
3. Use single orchestrator script (no sequential calls)
4. Include usage examples in your response
5. Minimize context passed to subsequent requests

## Prompt Prefix
/skills:tool-optimizer
```

### CLI Usage Examples

```bash
# With tool optimizer skill
codex /skills:tool-optimizer "Write GitHub integration script"

# With explicit scope narrowing
codex --scope "src/api" "Fix authentication bug"

# Multi-request task (chunked)
codex --plan "Refactor database layer"
codex --read "src/db" 
codex --patch "Apply optimizations"
```
